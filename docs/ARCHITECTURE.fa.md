# راهنمای طراحی نور: چرا هر قسمت را این‌گونه نوشتیم؟

این سند برای یادگیری بعد از مشاهده کد واقعی است. پیش از تغییر هر کلاس، مسیر اجرای یک درخواست را دنبال کن:

`Browser → Apache Rewrite → public/index.php → bootstrap → Request → Router → Middleware → Controller → Response → Browser`

## ۱. چرا هسته جدا از برنامه است؟

`src/Noor/` کدهای عمومی فریمورک است؛ `app/` کدهای اختصاصی برنامه. این جداسازی باعث می‌شود Noor در پروژه‌های گوناگون قابل استفاده باشد، بدون اینکه هسته از جدول‌ها، داده‌ها و قواعد کاری آن پروژه‌ها اطلاع داشته باشد.

## ۲. چرا Composer نداریم؟

با `spl_autoload_register` وقتی اولین بار کلاسی با Namespace `Noor\\` یا `App\\` موردنیاز شد، مسیر فایل از نام کلاس ساخته می‌شود. مزیت: اجرای مستقل و تعداد ابزار کمتر. هزینه: خودمان مسئول سازگاری مسیرها، نسخه‌بندی و نگهداری هستیم. Composer بد نیست؛ برای اهداف این پروژه عامدانه حذف شده است.

## ۳. چرا Router اطلاعات Route را هنگام ثبت آماده می‌کند؟

الگوی `/products/{id}` به Regex تبدیل می‌شود تا در زمان درخواست، مقدار شناسه استخراج شود. ساخت Regex هنگام ثبت Route باعث می‌شود منطق ثبت از اجرای درخواست جدا باشد. `preg_quote` متن ثابت را محافظت می‌کند. مسیر ثابت قبل از مسیر پویا اجرا می‌شود تا `/products/new` به‌جای `id=new` به Route اختصاصی برسد.

## ۴. چرا 404 با 405 فرق دارد؟

404 یعنی مسیر پیدا نشد؛ 405 یعنی مسیر وجود دارد ولی HTTP Method مجاز نیست. در پاسخ 405، هدر `Allow` متدهای مجاز را اعلام می‌کند. این رفتار برای ابزارهای API و عیب‌یابی روشن‌تر است.

## ۵. چرا Request و Response شیء هستند؟

با `Request` ورودی‌های HTTP را یک‌بار جمع می‌کنیم و به Controller می‌دهیم؛ برای تست می‌توانیم بدون Apache یک Request ساختگی بسازیم. `Response` کد وضعیت، بدنه و هدر را یکجا نگه می‌دارد. کنترل هدر و Redirect از خطاهای تزریق هدر یا هدایت به دامنه ناخواسته جلوگیری می‌کند.

## ۶. چرا Middleware وجود دارد؟

Middleware یک تابع با ورودی `(Request $request, callable $next): Response` است. می‌تواند پیش از Controller دسترسی را رد کند یا بعد از اجرای آن هدر اضافه کند. CSRF و Auth نباید برای هر Controller دوباره نوشته شوند. Middleware کلی و Middleware هر Route هر دو پشتیبانی می‌شوند.

## ۷. چرا View خودش خروجی را Escape نمی‌کند؟

Viewهای PHP می‌توانند HTML بنویسند و داده‌های متغیر را نمایش دهند. موتور View نمی‌داند یک مقدار داخل متن HTML، Attribute، URL یا JavaScript قرار گرفته است. بنابراین `View::escape()` را **در محل نمایش متن HTML** استفاده می‌کنیم؛ برای زمینه‌های دیگر باید روش مناسب همان زمینه را انتخاب کنیم. محدود کردن مسیر View مانع `../` و دسترسی به فایل‌های خارج از پوشه قالب می‌شود.

## ۸. چرا PDO و Prepared Statement؟

PDO اتصال به دیتابیس و Prepared Statement را فراهم می‌کند. مقدار متغیر کاربر را هرگز با الحاق رشته داخل SQL قرار نمی‌دهیم. تراکنش چند دستور مرتبط را با `commit` یا `rollback` هماهنگ می‌کند؛ این ویژگی برای هر عملیاتی که چند تغییر مرتبط در دیتابیس دارد، مانند ثبت سفارش به همراه اقلام آن، کاربرد دارد. اعتبارسنجی و مجوز کاربران همچنان در سطح برنامه انجام می‌شود.

## ۹. چرا مدیریت خطا در Application است؟

اگر خطایی از Router یا Controller خارج شود، `Application` آن را در Log ثبت می‌کند و به کاربر پاسخ 500 می‌دهد. در محیط عملیاتی متن خطای داخلی نباید نمایش داده شود. Log حاوی اطلاعات حساس احتمالی است و نباید عمومی باشد.

## ۱۰. نسخه پایدار و محدودیت‌های آزمون

برچسب Stable یعنی API فعلی برای استفاده و توسعه تثبیت شده است، نه اینکه همه شرایط عملیاتی تأیید شده باشند. تست‌های خودکار بخش‌های مشخصی از هسته را پوشش می‌دهند. در محیط ساخت، درایور PDO/MySQL موجود نبود؛ بنابراین تست واقعی اتصال دیتابیس، تراکنش‌های هم‌زمان، تنظیمات Apache و XAMPP، بار عملیاتی، مجوز فایل‌ها و امنیت نرم‌افزار نهایی همچنان باید روی محیط مقصد انجام شود.

## ۱۱. مسیر یادگیری پس از دریافت پروژه

درس اول: راه‌اندازی، Front Controller و جریان HTTP. درس دوم: Autoload و Namespace. درس سوم: Request/Response و تفاوت وضعیت HTTP. درس چهارم: Router و Regex و اولویت Route. درس پنجم: Controller، View و Contextual Escape. درس ششم: Middleware و Session و CSRF. درس هفتم: PDO، SQL و تراکنش. درس هشتم: نوشتن تست و اشکال‌زدایی. درس نهم: ساخت یک ماژول CRUD مستقل با استفاده از Noor. در هر درس فایل واقعی را خط‌به‌خط باز می‌کنیم و بعد یک تمرین انجام می‌دهیم.
